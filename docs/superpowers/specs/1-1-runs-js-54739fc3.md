## Behaviour

### `alertNotification(run, state, project, runId)` → `{title, body}`

- `run`: a normalised run (the `normalizeRun` shape) or null when the snapshot failed.
- `state`: `"escalated"` or `"dead"`, the alert line's state.
- `project`: the project's display name.
- `runId`: the alert line's run id, used when `run` is unusable.

Returns a fresh plain object with exactly the keys `title` and `body`, both strings.

**Usable run.** `run` is usable when it is an object (not an array) whose `id` is a
non-empty string (`_isObject(run) && _isRunId(run.id)`). Anything else — `null`,
`undefined`, a number, a string, an array, `{}`, an object whose `id` is missing, `""` or
not a string (what `normalizeRun` makes of garbage) — is unusable. `run.id` is not compared
with `runId`.

**Run title (`<title>` below).**
- Usable run: `runTitle(run)` (its `milestone_id`, else its short id).
- Unusable run: the short id of `runId`: `"…"` plus its last 8 characters (all of a shorter
  one); `"…"` alone when `runId` is not a string (same rule as `shortId`).

**Project suffix.** When `project` is a non-empty string the suffix is `" · " + project`
(space, U+00B7, space, the project verbatim). When `project` is `""`, not a string, null
or undefined, the suffix is `""` — the ` · ` part is dropped entirely.

**Wording by state** (parent lines 92-96):

| state | title | body (usable run) | body (unusable run) |
|---|---|---|---|
| `"dead"` | `✖ <title> died<suffix>` | `process died` | `process died` |
| anything else | `‼ <title> escalated<suffix>` | `escalationReason(run)` | `escalated` |

`‼` is U+203C and `✖` U+2716, each followed by one space. Any `state` other than exactly
`"dead"` (including `"escalated"`, `""`, null, other strings) takes the escalated row: the
helper only emits the two states, and an alert must still produce a notification rather
than throw or render empty.

**Never throws** for any combination of argument types, including no arguments at all
(`alertNotification()` gives `{title: "‼ … escalated", body: "escalated"}`).

### Examples

With `status-escalated.json` normalised (`milestone_id`
`f18d342f-4887-4cd8-a86e-dd2755237c2c`), state `"escalated"`, project
`omarchy-project-manager`:

- title `‼ f18d342f-4887-4cd8-a86e-dd2755237c2c escalated · omarchy-project-manager`
- body `phase 'review' gate 'review_blockers_gate' failed: blocked=review, detail=review left 1 unresolved blocker(s): the review-fail marker names m3/task-b1-only-subtask-of-10e26d57`
  (equal to `Runs.escalationReason(run)`, already pinned at tst_runs.qml:1409-1415).

With `run = null`, state `"dead"`, project `""`, runId `20261008T143755Z-f18d342f`:
title `✖ …f18d342f died`, body `process died`.

## Tests

All in `tests/core/domain/tst_runs.qml`, the existing QML `TestCase` for `runs.js` (tier:
QML unit test via `qmltestrunner`; `alertNotification` is a pure `.pragma library` function,
so the unit tier is the cheapest tier that executes it, and the fixture loader `amRun` and
`mkRun` (tst_runs.qml:15, 871) already live there). Add them after the `newAlerts` tests.
Expected strings are written out literally in the tests, not rebuilt from `runTitle` /
`shortId`, except the fixture body, which is compared with `Runs.escalationReason(run)` and
with the literal reason.

1. `test_alertNotification_escalated_fixture` — normalised `status-escalated.json`, state
   `escalated`, project `omarchy-project-manager`: the title and body of the first example.
2. `test_alertNotification_dead` — `mkRun("20261008T000000Z-deadbeef", "started", false)`
   (milestone `m1`), state `dead`, project `alpha`: title `✖ m1 died · alpha`, body
   `process died`.
3. `test_alertNotification_title_without_milestone` — `mkRun(..., { milestone_id: "" })`
   for both states: the title uses the run's short id (`‼ …deadbeef escalated · alpha`,
   `✖ …deadbeef died · alpha`).
4. `test_alertNotification_fallback_without_run` — for each of `null`, `undefined`, `5`,
   `"x"`, `[]`, `{}`, `{ id: "" }`, `{ id: 7 }`, with runId `20261008T143755Z-f18d342f` and
   project `alpha`: escalated gives `‼ …f18d342f escalated · alpha` / `escalated`; dead gives
   `✖ …f18d342f died · alpha` / `process died`. Also a garbage run carrying a milestone
   (`{ milestone_id: "m9" }`, no id) still falls back to the runId's short id.
5. `test_alertNotification_short_runId_and_garbage_runId` — null run, runId `"abc"` gives
   `…abc`; runId `null`, `7`, `undefined` gives `…`.
6. `test_alertNotification_empty_project` — fixture run and null run, project `""`, `null`,
   `undefined`, `5`: titles end at `escalated` / `died`, with no ` · `.
7. `test_alertNotification_other_state_is_escalated` — states `""`, `null`, `"running"`,
   `"DEAD"`: the escalated row (with a usable run, body `escalationReason(run)`).
8. `test_alertNotification_shape_and_purity` — the result's sorted keys are exactly
   `["body", "title"]`, both strings; two calls return distinct objects; the run passed in
   is deep-equal (`JSON.stringify`) to itself before the call; `alertNotification()` with no
   arguments returns `{title: "‼ … escalated", body: "escalated"}`.

The full gate is `bash tests/run.sh` (pytest including `tests/architecture`, then every
`tst_*.qml` offscreen); it must stay green.

## Review focus for the planner

- A run object present but with an empty id (a normalised failed snapshot) must fall back to
  `runId`, not render `…` (test 4, `{}` / `{ id: "" }`).
- `project` of whitespace only is a non-empty string and is shown verbatim; not trimmed.
- The middle dot is U+00B7 with one plain space on each side; a wrong dot or NBSP is a
  silent mismatch in the title (tests compare whole strings).
- The fixture's milestone id is the full UUID, not a short id (runTitle returns the milestone
  verbatim).
